# Итерация 3: Звук через WebAudio (без файлов) + плавная анимация перемещения игрока

## Заголовок
Добавить процедурные звуковые эффекты через WebAudio API (щелчок хода/стены, подбор сундука, взрыв, укус медведя, арсенал/госпиталь, река/дырка, победа/поражение) и лёгкую плавную анимацию перемещения игрока (lerp) между клетками, чтобы игра ожила без новых зависимостей и без раскрытия тумана.

## Мотивация
Сейчас движение дискретно-резкое: игрок «прыгает» по клеткам, а все события (стена, подбор, ранение) — просто текст вверху. Это делает игру безжизненной: ни одного подтверждающего сигнала, кроме строки последнего log. Звук — самый дешёвый способ дать мгновенную тактильную отдачу каждому действию (стоит несколько строк, без файлов, через WebAudio), а плавное движение превращает мир из статичной сетки в живой лабиринт и сильно поднимает «ощущение дороговизны» игры. Обе механики не трогают логику тумана (радиус 1), не требуют зависимостей и не расширяют информацию игроку — только оформляют то, что он уже видит. Плавная анимация не даёт информации о дальних клетках, т.к. камера уже привязана к игроку.

Приоритизация (effect/стоимость): звук — максимально дёшево и заметно; анимация — умеренно дёшево и сильно украшает. Счёт/заметки/обучение проигрывают, т.к. прогресс и цель уже дают уровни/компас/overlay.

## Конкретное ТЗ

### 1. Звуковой движок — одна функция `sfx(type)`
Добавить новый блок после блока «Случайности» (перед «Состояние»):
```js
// ========== Звук (WebAudio, без файлов) ==========
let actx = null;
function sfx(type){
  try{
    actx = actx || new (window.AudioContext||window.webkitAudioContext)();
    if(actx.state==='suspended') actx.resume();
    const t0 = actx.currentTime;
    const o = actx.createOscillator();
    const g = actx.createGain();
    o.connect(g); g.connect(actx.destination);
    const P = {
      move:   [340,'sine',   .06,.08],
      wall:   [120,'triangle',.05,.18],
      chest:  [660,'sine',   .12,.25],
      bomb:   [70, 'sawtooth',.25,.40],
      bear:   [220,'square', .15,.30],
      heal:   [440,'sine',   .20,.22],
      river:  [520,'sine',   .25,.20],
      hole:   [160,'sine',   .18,.25],
      win:    [880,'sine',   .35,.35],
      lose:   [90, 'sawtooth',.4,.40],
      aim:    [500,'sine',   .08,.15],
    }[type];
    if(!P) return;
    const [freq,wave,dur,vol] = P;
    o.type=wave; o.frequency.value=freq;
    g.gain.setValueAtTime(vol, t0);
    g.gain.exponentialRampToValueAtTime(.001, t0+dur);
    o.start(t0); o.stop(t0+dur);
  }catch(_){ /* без звука игра всё равно работает */ }
}
```
Всегда оборачивать в `try/catch`: если AudioContext недоступен, игра работает молча — звук строго опционален. `actx` создаётся лениво при первом звуке (первый клик пользователя), что соблюдает политику автозапуска браузеров.

### 2. Куда вставить вызовы `sfx(...)`
Вызывать в точках событий, рядом с уже существующими `msg(...)`:

- **`tryMove`** — после успешного шага: `sfx('move')`; в ветке «Стена!»: `sfx('wall')`.
- **`bomb`** — при удачном взрыве (`wall[...]=false`): `sfx('bomb')`; при «Здесь нет стены» — не звучать (или `sfx('wall')`, на выбор, но консистентно).
- **`onEnter`**:
  - река (`riverJump`): `sfx('river')`;
  - дырка: `sfx('hole')`;
  - арсенал: `sfx('heal')`;
  - госпиталь: `sfx('heal')`;
  - сработавшая ловушка (ранение): `sfx('bear')` (грубый «удар»);
  - подбор сундука (`carrying=true`): `sfx('chest')`.
- **`bearTurn`** — при контакте медведя с игроком (ранение): `sfx('bear')`.
- **`endWin`**: `sfx('win')`.
- **`endLose`**: `sfx('lose')`.
- **`endTimeout`**: `sfx('lose')`.
- **Клавиша `KeyB` при входе в режим `aiming`**: `sfx('aim')` (короткий «пик» — сигнал, что ждём направление).

Не дублировать звук, если событие не происходит (например, «Стена» в `bomb` — только когда реально дошли до взрыва).

### 3. Плавная анимация перемещения игрока — лёгкий lerp
Цель: игрок плавно «скользит» из текущей клетки в новую, мир и камера рисуются относительно его реальной экранной позиции. Логика позиции `player` НЕ меняется — это по-прежнему дискретная клетка; анимация — чисто визуальный слой поверх.

#### 3.1 Переменные состояния рендера
В блок «Состояние» добавить:
```js
let camR = 0, camC = 0; // фракционное смещение камеры (0..1 к следующей клетке)
let moving = false;     // идёт ли анимация
let spd = 10;           // скорость lerp (чем больше, тем плавнее и дольше; ~7..14)
```
Дополнительно нужна «отрисовочная» позиция игрока. Проще всего использовать перенос начала координат канваса на `C - camC*CS, C - camR*CS` и рисовать игрока всегда в центре `(C, C)`. Тогда камера плавно двигается, а игрок остаётся в центре — совпадает с текущей «камера за игроком».

#### 3.2 Инициализация покадрового цикла
Добавить в конце `init()`: `camR=0; camC=0; moving=false;` и обеспечить запуск `requestAnimationFrame`. Ввести единый анимационный цикл:
```js
function frame(){
  if(moving){
    // приблизить cam к цели (1,1) целевого смещения
    const step = spd*0.016; // ~60fps поправка
    camR += (1-camR)*Math.min(1,step); // camR идёт от 0 к 1
    camC += (1-camC)*Math.min(1,step);
    if(camR > 0.999 && camC > 0.999){ camR=1; camC=1; moving=false;
      // аккуратно переключить цель после остановки (см. 3.4)
    }
  }
  render();
  requestAnimationFrame(frame);
}
```

**Важно про дизайн лерпа**: `camR/camC` всегда движутся к `(1,1)` и по завершении сбрасываются в `0` при смене клетки. Схема:
- `player` — дискретная клетка, где игрок «логически».
- В момент хода: `camR=camC=0`, `moving=true`, камера рисует позицию предыдущей клетки как текущий экранный центр, а затем `camR/camC → 1` сдвигает изображение так, что к концу в центре оказывается новая клетка.

Это требует, чтобы `render()` пересчитывал преобразование координат с учётом `camR/camC`. Заменить в `render()`:
```js
const sx = r => C + (r - pr) * CS;
const sc = c => C + (c - pc) * CS;
```
на (где `pr/pc` — прежняя клетка перед анимацией):
```js
// видимая позиция игрока смещается на camR/camC от pr к pr+dr
const drawR = pr - camR;   // логическая «нарисованная» клетка (0..1 в прошлую)
const drawC = pc - camC;
const sx = r => C + (r - drawR) * CS;
const sc = c => C + (c - drawC) * CS;
```
Игрок рисуется по-прежнему в центре `(C,C)` — он не двигается на экране, движется весь мир под ним. Это соблюдает «камера привязана к игроку, игрок в центре».

Когда `moving=false` и `camR=camC=0`, `drawR=pr`, `drawC=pc` — рендер идентичен текущему. **Регрессия отсутствует в статике.**

#### 3.3 Инициирование анимации по ходу
Всю анимацию двигает только ход игрока. В `tryMove` после успешной смены `player`:
```js
const fr=pr, fc=pc; // запомнить старую позицию ДО изменения player
player = [r+dr, c+dc];
```
Нужно хранить прежнюю клетку для анимации. Добавить в `tryMove` перед `player = [...]`:
```js
// запомнить точку старта анимации (старая клетка)
animFrom = [r,c]; // глобальная переменная
if(!moving){ camR=camC=0; }
moving = true;
```
где `animFrom`, `camR/camC` — глобальные. Без этого потеряем стартовую клетку: если рисовать от текущей `player`, lerp «прыгнет» в уже новую клетку. Схема: камера стартует так, что в центре старая клетка, и за ~10 кадров «приезжает» к новой.

**Более простая и надёжная схема (рекомендуется)**: хранить в `camR/camC` прогресс 0→1, где 0 = игрок всё ещё в `animFrom`, 1 = игрок в `player`. В `tryMove`:
```js
animFrom=[r,c]; moving=true; if(camR>0&&camC>0){/*не перезапускаем резко*/}
```
И в `render`:
```js
const drawR = animFrom[0] + (player[0]-animFrom[0]) * ease; // ease = camR
const drawC = animFrom[1] + (player[1]-animFrom[1]) * camC;
```
Но т.к. игрок двигается строго на 1 клетку (или телепортируется), `player-animFrom` — единичный вектор либо скачок (река/дырка). Для телепортов (река на 2 звена, дырка) плавность не нужна — мгновенный перенос лучше. Смягчить: если расстояние >1 клетки, ставить `camR=camC=1; moving=false;` сразу (без анимации), чтобы телепорт был резким как сейчас.

**Итоговая формула в `render()`** (замена блока `sx/sc`):
```js
const pr = player[0], pc = player[1];
const e = Math.min(1, (camR+camC)/2); // общий прогресс анимации
let drawR = pr, drawC = pc;
if(moving && animFrom){
  drawR = animFrom[0] + (pr-animFrom[0])*e;
  drawC = animFrom[1] + (pc-animFrom[1])*e;
}
const sx = r => C + (r - drawR)*CS;
const sc = c => C + (c - drawC)*CS;
```

#### 3.4 Как поймать момент завершения и не сломать следующий ход
Игрок может нажать стрелку, пока анимация идёт (быстрая серия ходов). Чтобы не накапливать анимации и не допустить «гуляние» камеры:
- При новом ходу, если `moving` уже true, **ускорить**: `camR=camC=1` (мгновенно завершить текущую), затем перезапустить lerp к новой цели. Практично: в `tryMove` сразу ставить `camR=camC=0; moving=true; animFrom=прежняя клетка;`.
- Для телепортов (дистанция >1 либо скачок): `camR=camC=1; moving=false;` и не трогать `animFrom` (drawR/drawC = pr/pc — стабильно).

Это означает: при каждом успешном ходе камера мягко съезжает из старой в новую клетку; при быстром двойном шаге вторая анимация мгновенно завершает первую и стартует из неё — будет заметный лёгкий «рывок», но он допустим и лучше, чем накопление.

#### 3.5 `frame()` и запуск
Добавить функцию `frame()` как в п.3.2 (без смены цели на остановке — схема из 3.4 уже держит цель через `animFrom`), и в конце `init()` вызвать однократно `requestAnimationFrame(frame)`. Таймер (setInterval на 1с) НЕ менять — он живёт параллельно. render() вызывается каждый кадр вместо только при событиях — но это дёшево и снимает логику «вызывать render() вручную» (её можно оставить, повторный вызов безвреден).

> Обоснование непрерывного `requestAnimationFrame`: постоянно рендерить канвас 10x10 в 3x3 видимой зоне — тривиально дёшево, даже связных мелочей мало. Это самый простой способ анимации без инвалидации кадров. (Если хочется строже — можно рендерить только когда `moving` или изменилось состояние, но это усложнение, не требование.)

### 4. Остановка анимации в концовках
В `endWin/endLose/endTimeout`: `moving=false; camR=camC=1;` (выровнять камеру), чтобы overlay показывался на устойчивой картинке. `frame()` продолжит крутиться, но при `moving=false` рисует статичный кадр — безвредно.

Также стоит установить `moving=false` в `init()` (новый уровень — анимация сбрасывается).

## Что нельзя трогать (регрессионная защита)
- **Логика позиции `player`**: это по-прежнему дискретная клетка `[r,c]`. Анимация — только визуальный слой; ВСЕ механики опираются на `player`, `wall`, `bearTurn`, `riverJump`, `nextHole`, `bomb`, `carrying`, `activeTarget()`, `moves`, `health`, `bombs`, `over` — без изменений.
- **Туман** `visible(r,c)`: видимы только клетки в радиусе 1. `drawR/drawC` не влияют на `visible` — функция использует `player` (дискретную), не draw-позицию. Никакого раскрытия дальше радиуса 1.
- **Генерация карты**, раскладка объектов `init()`, `genWalls`, `ensureConnected`, `reachable`, прогрессия уровня.
- **Механики**: `tryMove` (логика хода/стены), `bearTurn`, `bomb`/`aiming`, река, дырки, арсенал, госпиталь, ловушки, подбор сундука/выход, `endWin/endLose/endTimeout`, таймер `LEVEL_TIME`/setInterval.
- **HUD** (здоровье/бомбы/клад/компас/время), пульс-стрелка, клавиши, кнопки рестарта/overlay. Overlay и его поведение не меняются.
- **`render()`** в целом: отрисовка клеток/стен/медведей/игрока/пульса не переписывается — меняется только верхнее преобразование координат (`sx/sc`) и добавляется вызов `sfx(...)` в события. Формула `sx/sc` при `moving=false, camR=camC=0, animFrom=null` тождественна текущей.
- Камера по-прежнему привязана к игроку, игрок рисуется в центре `(C,C)`.

## Критерий приёмки
1. **Звук**: каждый шаг — мягкий щелчок; удар в стену — низкий «тук»; подбор сундука — светлый двухтоновый «звяк»; взрыв — низкий гул; укус медведя/сработавшая ловушка — грубый звук; арсенал/госпиталь — спокойный «аккорд»; вход в режим бомбы (B) — короткий пик; победа/поражение — отдельные тона. Звук не обязателен: в браузере без аудио (или до первого клика) игра работает как раньше.
2. **Анимация**: при одиночном ходе игрок плавно скользит из клетки в клетку (~0.1–0.15 с), мир «подъезжает» под него; игрок остаётся в центре. В статике (не двигаешься) картинка идентична итерации 2.
3. **Быстрые ходы**: серия быстрых нажатий не ломает позицию игрока — в итоге он попадает в те же клетки, что и без анимации (дискретная логика совпадает; возможен лёгкий визуальный рывок при двойном шаге).
4. **Телепорты**: река и дырка переносят мгновенно (дискретно), без плавного «пролёта» по несуществующим клеткам.
5. **Концовки**: overlay появляется на устойчивой (не движущейся) картинке; таймер, уровни, счёт ходов, компас работают как в итерации 2.
6. **Регрессия тумана**: во время анимации не появляется ни одной невидимой ранее клетки; `visible()` даёт ровно тот же видимый радиус, что и до изменений.

## Риски
- `requestAnimationFrame` крутится постоянно. Для карты 10x10 с видимой зоной 3x3 это дёшево, но если в будущем добавить много объектов — стоит перейти к прицельному ре-рендеру по инвалидации. Мониторить FPS при медведи/ловушки на поздних уровнях.
- Lerp-схема с `animFrom` самая капризная часть: важно сохранить формулу `draw = from + (to-from)*e` и сбрасывать `camR/camC` в 0 при каждом новом ходе. Рекомендуется: при расстоянии (`|pr-aFrom[0]|+|pc-aFrom[1]|`)≠1 (река/дырка/край) ставить `moving=false` без анимации.
- Звук через WebAudio требует первого пользовательского жеста для `resume()`; до этого звуков нет — это нормально, прятать под `try/catch`.
